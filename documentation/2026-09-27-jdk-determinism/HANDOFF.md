## 2. What was found

- **Sweep**: 36 Linux x64 runtimes (Temurin 21.0.2 to 27, Zulu, Corretto, Microsoft, Liberica, Oracle JDK, Oracle OpenJDK, SapMachine, Dragonwell, Kona, Ubuntu OpenJDK; GraalVM CE and Oracle GraalVM 21 and 25; IBM Semeru OpenJ9 21.0.5, 21.0.10, 25.0.2), one javac build run under each: the 249 fluid runtime tests with the 33 junction ledger lines, chain-100 exact, the hex bitwise probe, and a `Math` vs `StrictMath` sweep of 1,048,576 inputs per function.
- **Three result families**, byte-identical inside each: A = every HotSpot 21-24 and GraalVM 21 (22 runtimes); B = every HotSpot 25-27 and GraalVM 25 (11): 24 of 33 junction lines and 2,721 of 3,003 chain-100 numbers differ from A (max 8.0e-15 relative); C = OpenJ9 (3): 28 lines, 2,719 numbers (max 5.7e-15). Every test passes everywhere; only the printed doubles move.
- **Cause: the libm only.** HotSpot intrinsics for `Math.log/exp/pow/cos/log10` differ from fdlibm by 1 ulp (log10 2 ulp) on 3-8 % of inputs; JDK 25 added a `cbrt` intrinsic (family B, the Peng-Robinson cubic roots); OpenJ9's `Math` is fdlibm; HotSpot with `-XX:-UseLibmIntrinsic` reproduces OpenJ9 byte for byte. `Math.sqrt` and `Math.fma` are identical on all 36 (JLS). GraalVM CE 25's compiled `pow` even depends on warm-up. The owner's Windows 21.0.11 line matches no Linux runtime (Temurin 21.0.11 included): inferred to be the Windows path of the same functions (review 7.3); verify on Windows with `java tools/jdk-determinism/src/MathSweep.java`.
- **The column V3 solver is JDK-dependent today as well** (base code): its suite passes only on HotSpot 21-24; OpenJ9 fails 4 column tests, HotSpot 25 fails 3 others (review 7.4).

## 3. The fix, prototyped

- `science/math/DeterministicMath`: one facade returning the `StrictMath` (fdlibm) result bit for bit for every non-correctly-rounded function on the fluid path (91 call sites in 13 files: `science/fluid/**`, `science/thermo/PengRobinson78`, `PengRobinsonKernel`, `science/material/ViscosityCorrelation`, `science/column/v3/thermo/V3WaterProperties`); `Math.sqrt`/`Math.fma` and the exact functions stay. `pow` is an allocation-free transliteration of netlib fdlibm `e_pow.c` (`FdlibmPow`, Sun's permissive licence, no OpenJDK code) because JDK 21-27's `StrictMath.pow` allocates 96 B per call and costs 7x; equal to `StrictMath.pow` on 1.5e9 inputs across five runtimes and under `-Xint`.
- Guard: `DeterministicMathSourceTest` (in `fluidScienceTest`) fails on any direct `Math`/`StrictMath` log/exp/pow/cbrt/trig call in `science/` (column exempt pending decision 2), `runtime/` and the benchmark fixtures; `DeterministicMathTest` checks the `pow` equivalence and zero allocation.
- **Result**: all 36 runtimes byte-identical (junction lines, chain-100 exact 0.000e+00, all probe files), with or without libm intrinsics. The new outputs are bit for bit what OpenJ9 produced on the base code.
- **Cost** (container JDK, harness runtime suite, alternated runs): wall 54.8 s -> 64.2 s (+17 %), `MIXED_GAS_COST` 449 -> 655 ms (+46 %), 286 Newton solves unchanged, allocation unchanged; all of it `pow`. Optional `tools/jdk-determinism/pow-strength-reduction.patch` (10 lines: integer-exponent `pow` calls in `PipeResistance` and `TranslatedPengRobinson` as multiplications) returns both to base (53.8 s, 445 ms), one more ulp re-baseline.
- **Re-baseline (one time)**: 28 of 33 junction lines (old/new in review 10.3), `chain-100.json` (max 5.657e-15 relative moles, 3.4e-13 K, 2.7e-14 kg/s; same 3/0 steps, 4 solves, 29 iterations), printed diagnostics of 20 fluid test classes, step counts +-1-2 in `PhasePortPriorityTest` and `LevelHeadTest`; no assertion or tolerance changed.
- **Gates on the prototype** (review 11): fluid suites 477/477 (472 + 5), exact regression 0.000e+00 after re-capture, adjacent 45/45, GameTest and mcpCompat compile green, harness `all` green; full `test` 1169/1171: `V3LearnedRecoveryTest.theRampHandoffRecoversACappedCorrectionOnAnAuthoredDrawColumn` and `V3NearbyInputRecoveryTest.nearby551KelvinColdInputPassesTheSameFreshAcceptanceGate` go to nonconvergence because the column now mixes fdlibm water properties with intrinsic thermodynamics (decision 2). `tools/jdk-determinism/full-science-routing.patch` (whole science tree) makes the column deterministic and fails exactly the 4 column tests OpenJ9 fails today.
