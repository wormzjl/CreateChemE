# Fluid transport mods on Minecraft 1.21.1

Update, 15 September 2026: an executable benchmark and actual measurement work now accompany this original source study. See [measurement results](../../benchmarks/fluid-pipes-1.21.1/RESULTS.md). The original research below distinguishes source-based predictions from the later measured results.

Research date: 14 September 2026. Scope: primarily **NeoForge 1.21.1**, matching CreateChemE; Oritech also provides a Fabric build. This is a functional comparison and source-based performance study, with a reproducible benchmark protocol. **No comparative runtime measurements were performed. There is no measured performance winner.**

The most useful distinction is between **endpoint transfer**, **shared network storage**, and **local pipe state/transport**. Pipe count alone cannot describe a workload. A 10,000-block cable connecting two tanks can be cheaper than 200 blocks connecting hundreds of actively queried tanks. Conversely, a system can appear cheap because it is slow, blocked, out of range, or failing to reach the destination.

“Major” here means established transport systems and prominent industrial-mod alternatives, covering different designs; this is not a download-count ranking or an exhaustive catalog. Public project pages establish version availability. Release source establishes implementation details where inspected. Performance predictions below are hypotheses, not benchmark results.

**What the implementations imply.** Each paragraph separates an observed mechanism from a prediction to test. Source links are pinned to commits. Where no release tag was established, the manifest identifies an inspected branch snapshot; matching version text does not prove binary equivalence.

**Create:** `PumpBlockEntity` distributes pressure through the pipe topology. `FluidTransportBehaviour` updates connection/flow state; `FluidNetwork` discovers reachable targets and performs source/destination transfers. This is more nuanced than saying it moves a tankful of liquid from block to block. Its “pressure” controls game transport; these classes are not a general hydraulic/thermodynamic solver. Prediction: pipe count, pump count, branches, changing flow direction and pressure recalculation all deserve separate axes. [Pump implementation](https://github.com/Creators-of-Create/Create/blob/ac0c444d9828da3453ae8cc65338e8de063286fb/src/main/java/com/simibubi/create/content/fluids/pump/PumpBlockEntity.java), [flow behavior](https://github.com/Creators-of-Create/Create/blob/ac0c444d9828da3453ae8cc65338e8de063286fb/src/main/java/com/simibubi/create/content/fluids/FluidTransportBehaviour.java), [network transfer](https://github.com/Creators-of-Create/Create/blob/ac0c444d9828da3453ae8cc65338e8de063286fb/src/main/java/com/simibubi/create/content/fluids/FluidNetwork.java)

**Mekanism:** each mechanical-pipe block entity participates in server updates, including a pull check. Fluid distribution itself uses a network tank and cached acceptors. Consequently, item-transporter pathfinding results do not describe mechanical-pipe behavior. Prediction: there is a per-pipe baseline plus endpoint-distribution work, while topology changes and saving need separate investigation. [Pipe block entity](https://github.com/mekanism/Mekanism/blob/a00109e4856fd38b9c5b3dd7f22ce4a59cd65a80/src/main/java/mekanism/common/tile/transmitter/TileEntityMechanicalPipe.java), [fluid network](https://github.com/mekanism/Mekanism/blob/a00109e4856fd38b9c5b3dd7f22ce4a59cd65a80/src/main/java/mekanism/common/content/network/FluidNetwork.java)

**Pipez:** each extractor caches reachable connections. Its fluid implementation visits candidate destinations and source tanks and performs simulated/actual transfers. Round-robin distribution also uses repeated passes and scans of destination-full flags; it should not be assigned a simple linear complexity without measurement. Prediction: long stable lines with few extractors should be relatively favorable, while many extractors facing many blocked destinations or many-tank handlers can be expensive. Rebuilding separate extractor caches can multiply topology-discovery work. [Connection cache](https://github.com/henkelmax/pipez/blob/91a01deda19e5beb19fe7840aa14daaa312aa212/src/main/java/de/maxhenkel/pipez/blocks/tileentity/PipeTileEntity.java), [fluid transfer](https://github.com/henkelmax/pipez/blob/91a01deda19e5beb19fe7840aa14daaa312aa212/src/main/java/de/maxhenkel/pipez/blocks/tileentity/types/FluidPipeType.java)

**Modern Industrialization:** its network tick gathers targets from ticking nodes, sums network inventory, extracts/inserts by priority, redistributes inventory and calls node after-tick logic. Priority buckets are sorted, shuffled and simulated before execution. The cached ticking-node list includes network nodes in ticking chunks, not just machine endpoints. Prediction: expect a node-count term and endpoint/sorting/allocation terms, despite centralized network ownership. This is a useful shared-inventory design reference, not an endpoint-only implementation. [Network tick](https://github.com/AztechMC/Modern-Industrialization/blob/e0b405a1f24917db38cb5e82836511f3ad357afe/src/main/java/aztech/modern_industrialization/pipes/fluid/FluidNetwork.java), [ticking-node list](https://github.com/AztechMC/Modern-Industrialization/blob/e0b405a1f24917db38cb5e82836511f3ad357afe/src/main/java/aztech/modern_industrialization/pipes/api/PipeNetwork.java)

**Ender IO 8.2.12:** `FluidConduitTicker` iterates channels, extract connections, source tanks and insertion paths, applying filters and tracking transferred amounts per path. `FluidConduit` describes path rate limits and channel configuration. In this release the fluid conduit record has no old `is_multi_fluid` field; treating lower tiers as historical single-fluid reservoirs would misdescribe this implementation. Prediction: active endpoint/path/filter counts and network-cache rebuilds are more informative than simply counting conduit blocks. [Ticker](https://github.com/Team-EnderIO/EnderIO/blob/9d35cace6895f451b4478a8608ff0fa0506530a5/enderio/src/main/java/com/enderio/enderio/content/conduits/type/fluid/FluidConduitTicker.java), [conduit definition](https://github.com/Team-EnderIO/EnderIO/blob/9d35cace6895f451b4478a8608ff0fa0506530a5/enderio/src/main/java/com/enderio/enderio/content/conduits/type/fluid/FluidConduit.java)

**Immersive Engineering:** a fill call routes to cached reachable handlers. Discovery stops when the visited-pipe list reaches 1,024. Pipe removal clears the dimension's connection cache. Prediction: a stable route can be cheap, but reachability past the traversal bound and the breadth of rebuild work after an edit are important. The bound is a discovery limit, not proof that every network containing 1,025 blocks fails: starting point, topology and endpoint placement matter. Test a single-fed line with its sink beyond the bound, then branched layouts. [Released pipe implementation](https://github.com/BluSunrize/ImmersiveEngineering/blob/583a182549d284a35c813b55ac2a0d1fddcf945a/src/main/java/blusunrize/immersiveengineering/common/blocks/metal/FluidPipeBlockEntity.java)

**GregTech CEu 7.0.2:** the released block entity subscribes to server ticks, attempts fluid distribution on a five-tick cadence, maintains local tanks, examines adjacent sides and checks material/fluid incompatibilities. This is a useful contrast to shared reservoirs and endpoint teleportation. Prediction: occupied pipe count, local fluid channels, filling transients and material checks matter; greater fidelity/gameplay constraints can carry a real computational cost. The 7.0.2 artifact is alpha, so a benchmark must separately record functional failures. [Released pipe implementation](https://github.com/GregTechCEu/GregTech-Modern/blob/f6200e018582c3e26e8db06c289d9e01c8250ac8/src/main/java/com/gregtechceu/gtceu/common/blockentity/FluidPipeBlockEntity.java), [material properties](https://github.com/GregTechCEu/GregTech-Modern/blob/f6200e018582c3e26e8db06c289d9e01c8250ac8/src/main/java/com/gregtechceu/gtceu/api/material/material/properties/FluidPipeProperties.java)

**Oritech:** fluid interface entities select an extractable fluid and try cached targets, shuffling destination order. The target cache still involves a hash of the target set, so “cached” does not establish constant endpoint cost. Prediction: favorable sparse-line scaling is plausible, but many destinations, target-cache refreshes and maximum reachable size need direct tests. [Released interface implementation](https://github.com/Rearth/Oritech/blob/bf0d3e96b9a21e3b132d06a6be3c505b00588f00/common/src/main/java/rearth/oritech/block/entity/pipes/FluidPipeInterfaceEntity.java)

**XNet:** the fluid channel has a ten-tick scheduling gate, cached extractor/consumer collections and additional per-connector scheduling. Active transfer visits eligible sources and consumers and can check tank counts. Prediction: cable length should have little steady transfer cost once discovery has stabilized, but endpoint count and synchronized transfer bursts can dominate tail latency. [Fluid channel implementation](https://github.com/McJtyMods/XNet/blob/559b1d959811cf04021b51810f353d8c048cd65e/src/main/java/mcjty/xnet/apiimpl/fluids/FluidChannelSettings.java)

**LaserIO:** node logic caches cards, schedules extraction by card sleep/cadence, inspects source tanks and routes through channel-matching inserters. Stocking and exact-transfer modes add different work. Prediction: count active cards, candidate insertions and scheduled bursts; counting visible laser links alone misses the workload. [Node implementation](https://github.com/Direwolf20-MC/LaserIO/blob/4d278a6351a434d343fbf70d942baeeaf2607536/src/main/java/com/direwolf20/laserio/common/blockentities/LaserNodeBE.java)

| Mekanism | Basic → Ultimate: 2,000 / 8,000 / 32,000 / 128,000 mB capacity per pipe; 250 / 1,000 / 8,000 / 32,000 mB pull amounts | Capacity and pull rate are different. External pushing and endpoint limits affect effective throughput. |

**A defensible performance evaluation.** The accompanying [benchmark protocol](./BENCHMARK_PROTOCOL.md) specifies workloads, controls, measurement and acceptance criteria. Its essential requirements are:

1. Vary **pipe count**, **active sources**, **destinations**, **tank slots**, **fluid identities/components**, and **network changes** independently.
2. Measure both **equal offered load** and **maximum sustainable throughput**. Test identical acceptance demand and report which systems satisfy it.
3. Report server tick work in milliseconds, p95/p99, deadline misses, actual fluid delivered, destination starvation, and network recovery. Add allocation/GC and retained-memory measurements.
4. Separate steady-state running from startup, chunk loading, topology changes, saving, and client rendering.
5. Preserve mass and components. A broken, partially loaded or capacity-limited network must not win by doing less work.

Conceptually, use an empirical model such as:

`cost/tick ≈ a + bN + cA + dH + eS + fF + gR + hU`

Here N is loaded pipe nodes, A active extractors, H actual handler calls, S tank slots examined, F filter/component work, R rebuild work and U synchronization work. These are explanatory variables, not independent mathematical truths. Some mods have interactions such as A×destinations, repeated round-robin scans, endpoint sorting, and rebuild amplification. Instrument actual call counts and fit separate curves rather than forcing every system into one complexity formula.

The [Pipez project-page comparison](https://www.curseforge.com/minecraft/mc-mods/pipez) explicitly compares **item pipes** against Mekanism logistical transporters on **1.16.5 and 1.19.2**. It should not be reused as a 1.21.1 fluid benchmark. Likewise, “no lag” and “highly optimized” are design claims until the relevant workload and exact binary have been measured.

**What I would evaluate first.** For a manageable first round, test Create, Mekanism, Pipez, MI, Ender IO and XNet. They provide the existing Create integration baseline and five contrasting designs. Add Oritech and LaserIO next for cached/direct endpoint alternatives, and Modern Dynamics for a standalone attachment-based option. Include GT early if pipe material constraints or local inventory are design requirements. Add Integrated Tunnels, SFM and Pretty Pipes: Fluids when their control models are candidates for the actual factory.

For a long sparse route, **XNet, Pipez and Oritech are plausible low-cost candidates based on their designs**, not proven winners. For many machines on one shared network, there is no defensible ranking without measuring actual endpoint calls, blocked-output behavior and latency. MI and Mekanism deserve testing when network storage is desirable; Create and GT should be evaluated with the physical/gameplay behavior they provide included in the comparison.

**Implications for CreateChemE.** The workspace README describes planned multicomponent fluid transport and process equipment; that functionality is not implemented there yet. The following are design proposals derived from this study, not existing CreateChemE capabilities:

- Separate the block connectivity graph from the scientific process graph. Collapse degree-two pipe runs into segments between junctions, pumps, valves and equipment, retaining length/material parameters and any required physical storage.
- Use cached endpoint capability references and rebuild affected components when connections change. Measure removal, split, rejoin and chunk-boundary correctness before making optimization claims.
- Make the simulation fidelity explicit. Instant endpoint transfer, a well-mixed network reservoir, and finite-volume local transport have different residence time, mixing and pressure semantics. Graph compression must retain storage/delay when those are part of the intended model.
- Keep expensive mixture property/flash calculations out of individual pipe-block ticks. Reuse results only when thermodynamic inputs remain valid; conservation and revision checks still apply.
- For interoperability, test custom `FluidStack` components deliberately. Carrying several named fluid types is not the same as physically mixing their chemical compositions. Identity comparison, filtering and drain/fill matching may reject or separate component variants; the adapter must define how mixtures are represented and conserved.
- Establish a project-specific budget, for example a **proposed** 5 ms/tick fluid-system allocation at a chosen plant size, while retaining headroom inside the overall 50 ms tick period. This is a target to validate, not a performance result or universal safe budget.

The recommended deliverable from actual testing is a set of cost-versus-size and cost-versus-delivery curves, accompanied by functional failures and recovery distributions. A single “fastest pipes” bar chart would conceal the differences this study found.
